# IP-Roller Bot

Telegram-бот на Go, который «роллит» публичные/floating IP у облачных
провайдеров до попадания в заданную маску (CIDR или октетный паттерн) и
привязывает подходящий адрес к ВМ. Реализован по спецификации `ip-roller-bot-spec`.

## Как это работает

В Telegram: `/roll` → выбор провайдера → маска → число попыток → запуск.
Движок в цикле `allocate → match → release`: выделяет новый адрес, проверяет
против маски, не подошёл — освобождает и роллит снова; подошёл — резервирует и
кладёт в пул. Соблюдаются rate-limit (token bucket), дневные капы и backoff на 429.

## Архитектура

```
Telegram → bot (UI/FSM) → engine (roll loop + limiter + daily cap + backoff)
                              │  interface Provider
                              ▼
        provider-адаптеры ── storage (SQLite: пул, история, счётчики)
```

- `internal/bot` — команды, FSM-мастер `/roll`, inline-клавиатуры, `acl.go` (whitelist/админы). Не знает деталей провайдеров.
- `internal/engine` — `roller.go` (цикл), `limiter.go` (дневные капы), `mask.go` (CIDR + октетные паттерны).
- `internal/provider` — интерфейс `Provider`, `Account` (обёртка с уникальным ключом) + по адаптеру на сервис.
- `internal/registry` — собирает живые аккаунты из БД (+ дефолты типа из конфига), сид из config при первом старте, hot-reload.
- `internal/storage` — SQLite (pure-Go, `modernc.org/sqlite`): пул, история, счётчики, **accounts**, **allowed_users**.
- `internal/config` — YAML + `${ENV}`.

## Аккаунты и доступ

**Креды провайдеров хранятся в SQL** (таблица `accounts`), а не в env. На каждый
тип провайдера можно завести **несколько аккаунтов** (напр. два Timeweb) — у
каждого свой ключ `тип#id`, поэтому rate-limit и дневной кап считаются по
аккаунту независимо. Поля кред — JSON-блоб; неуказанные не-секретные поля
(region, auth_url, zone) берутся из дефолтов типа в `config.yaml`.

Источник правды — БД. `config.yaml`/env используются только для **сида при
первом старте** (если таблица `accounts` пуста). Дальше — команды бота.

**Доступ:** админы управляют аккаунтами и whitelist'ом. Задаются двумя способами
(складываются): в `config.yaml` (`telegram.admin_user_ids` / `allowed_user_ids`)
**или через env** — `TELEGRAM_ADMIN_IDS=123,456` и `TELEGRAM_ALLOWED_IDS=789`
(удобно для `.env`/Docker; свой ID — у @userinfobot). Плюс динамический whitelist
в SQL (`allowed_users`), управляется командами. Если пусто всё сразу — доступ
открыт всем (с предупреждением в логах).

**Добавление аккаунта — по шагам, кнопками.** 🔐 Аккаунты → ➕ Добавить аккаунт →
выбираешь провайдера → бот **сразу просит вставить токен** и остальные поля по
очереди (с подсказкой «где взять» и кнопкой «Пропустить» для необязательных).
Название можно не придумывать — жми «Пропустить», бот назовёт сам. Сообщения с
секретами бот старается удалить. JSON руками писать не нужно.

Текстом тоже можно (для тех, кому привычнее):
- `/addaccount timeweb <токен>` — для провайдеров с единственным секретом
  (Timeweb) достаточно вставить сам токен, label бот подставит.
- `/addaccount <тип> <label> <json>` — полный вид с JSON-кредами.
- `/addaccount <тип>` — гайд «где что взять».

Управление (только админ):

| Команда | Что делает |
|---------|------------|
| `/accounts` | список аккаунтов (секреты замаскированы) |
| `/addaccount <тип> <label> <json>` | добавить/обновить аккаунт; исходное сообщение с кредами бот удаляет |
| `/enableaccount <id>` · `/disableaccount <id>` | вкл/выкл аккаунт |
| `/delaccount <id>` | удалить аккаунт |
| `/users` | список доступа (админы/конфиг/whitelist) |
| `/adduser <id> [заметка]` · `/deluser <id>` | управление whitelist'ом |

Примеры: `/addaccount timeweb <твой_токен>` (быстро) или
`/addaccount timeweb prod {"token":"xxx","availability_zone":"spb-1"}` (полный).
`/addaccount` без аргументов печатает поля по каждому типу.

## Статус провайдеров

| Провайдер | Механика | Статус адаптера |
|-----------|----------|-----------------|
| **Timeweb** | floating IP (REST) | ✅ полностью реализован |
| **VK Cloud** | OpenStack/Neutron floating IP (gophercloud) | ✅ реализован |
| **Selectel** | OpenStack/Neutron floating IP (gophercloud) | ✅ реализован |
| **Gcore** | floating IP (REST `apikey`) | ✅ реализован: async-таски опрашиваются (`/v1/tasks`); `region_id` можно не задавать — роллит по любому региону |
| **MWS** | reserved IP в подсети (REST) | ✅ allocate/release; IAM-токен выдаётся `POST /iam/v2/tokens/:issueServiceAccountToken` c JWT в теле; attach — при создании ВМ |
| **RuVDS** | пересоздание/доп. IP сервера | ⚠️ каркас: allocate под защитой (нужен `server_id`, платно) |
| **Beget** | заказ доп. IPv4 / пересоздание VPS | ⚠️ каркас: allocate под защитой (нужен `server_id`, платно) |
| IHC/Contell/UFO/Vinton | панель без API | `internal/provider/cookie` — cookie-фолбэк (скелет) |

RuVDS/Beget намеренно не дёргают деструктивные/платные операции без явной
настройки сервера — Allocate возвращает понятную ошибку вместо порчи реальных
серверов. Эндпоинты заказа IP вписываются под конкретный аккаунт.

**Диагностика MWS.** Выпуск IAM-токена (self-signed ES256 JWT → IAM-токен через
`POST /iam/v2/tokens/:issueServiceAccountToken` с телом `{"jwt":…}`) восстановлен
из доки/аналога Yandex Cloud и **не проверен на живом API**. Если ловишь
`401 «JWS parsing attempt failed»` — запусти с `MWS_DEBUG=1`: бот напечатает в
stderr точный запрос, тело и **расшифрованные claims JWT** (header/payload) плюс
ответ сервера. Пришли эти строки (подпись JWT и токен вычисти — claims безопасны),
и форму запроса можно будет подогнать точь-в-точь. Быстрый обходной путь: положить
готовый токен из `mws iam create-token` в поле `token` (протухает за ~час).

## Запуск

```bash
cp .env.example .env      # заполни TELEGRAM_TOKEN и токены нужных провайдеров
set -a; source .env; set +a
go run ./cmd/bot -config config.yaml
```

Обязателен только `TELEGRAM_TOKEN`. Креды провайдеров в env — опциональны:
включённые блоки `config.yaml` с заданными `${...}` засеют аккаунты в БД при
первом старте; дальше добавляй аккаунты через `/addaccount`. Доступ ограничь
через `telegram.admin_user_ids` / `allowed_user_ids` (см. «Аккаунты и доступ»).

### Docker Compose

```bash
cp .env.example .env      # заполни TELEGRAM_TOKEN и токены нужных провайдеров
docker compose up -d --build
docker compose logs -f
```

- Бинарь собирается статически (`CGO_ENABLED=0`, SQLite pure-Go) в multi-stage
  образе на базе Alpine, запускается под непривилегированным пользователем.
- `.env` подхватывается через `env_file`; токены подставляются в `config.yaml`
  через `${...}` уже внутри приложения.
- `config.yaml` монтируется read-only — правь локально и `docker compose restart`.
- SQLite-база лежит на томе `botdata` (`STORAGE_DSN=/data/ip-roller.db` перекрывает
  `storage.dsn` из конфига), переживает пересоздание контейнера.
- Порты не публикуются: бот работает long-poll'ом, входящие соединения не нужны.

Остановка / обновление:

```bash
docker compose down              # остановить (том с БД сохраняется)
docker compose up -d --build     # пересобрать и поднять заново
docker compose down -v           # снести вместе с БД-томом
```

## Меню и команды

Бот рассчитан на одного админа: `/start` (или `/menu`) открывает **единое меню**
кнопками и **закрепляет его** в чате:
- 🎲 **Ролл** — пошаговый мастер (аккаунт → маска(и) → попытки → запуск), работает в том же сообщении.
- 📦 **Пул** — зарезервированные адреса (сохраняются сразу при попадании, видны и во время другого ролла).
- 📈 **Статистика** — сводка роллов/попаданий по всем аккаунтам + дневные лимиты и кулдауны.
- 🔐 **Аккаунты** — вкл/выкл, 📅 дневной кап, 🌐 прокси, 🎯 IP-пресеты, 🔁 авто-ролл, 🗑 удалить, ➕ добавить (мастер по кнопкам).
- 🌐 **Прокси** — добавить SOCKS5/HTTP-прокси и привязать к аккаунтам (через них идут запросы к API провайдера).

Повисшие непривязанные floating IP (кроме пула) **чистятся автоматически** перед каждым роллом.
Лимиты и квоты **уходят в топик** аккаунта и авто-обновляются после каждого ролла.
Всё делается кнопками; текстовые команды остаются как альтернатива:

### 🎯 IP-пресеты (цели на аккаунт)

У каждого аккаунта можно сохранить **маски-цели** (🔐 Аккаунты → 🎯): CIDR
(`185.12.0.0/16`) или октетный паттерн (`95.142.*.*`, `92.38.0-50.*`). Они
появляются кнопками в мастере ролла (шаг маски) и служат целями авто-ролла.
Хранятся в SQL (`account_masks`), удаляются вместе с аккаунтом.

### 🔁 Авто-ролл раз в сутки

Включи 🔁 у нужных аккаунтов (🔐 Аккаунты → 🔁) — и бот сам будет роллить их
раз в `autoroll.interval_hours` (по умолчанию 24 ч) по их 🎯 IP-пресетам, а итог
(пойман IP / без совпадений / ошибка) и обновлённую статистику **кладёт в топик
аккаунта**. Бюджет попыток настраивается там же; «🔁 Прогнать сейчас» запускает
разовый прогон вручную. Расписание переживает рестарт (`account_autoroll.last_run`).
Глобально выключается `autoroll.enabled: false`.

### Gcore: вставь ссылку вместо ID

На шаге `project_id` в мастере Gcore можно **вставить ссылку на проект** из
браузера (`https://cloud.gcore.com/projects/12345/regions/7/…`) — бот вытащит
`project_id` и `region_id` из URL. `region_id` можно **пропустить** — тогда роллит
по любому региону (перебирает доступные через `/v1/regions`).

Пользователь: `/menu` · `/roll` · `/pool` · `/attach <ip> <vm_id>` · `/limits` · `/cancel`

Админ: `/accounts` · `/addaccount` · `/delaccount` · `/enableaccount` · `/disableaccount` · `/users` · `/adduser` · `/deluser`

## Уведомления (форум-группа по топикам)

Лог ловли IP можно слать в отдельную **форум-супергруппу**: задай `NOTIFY_CHAT_ID`
(или `notify.chat_id`). Бот авто-создаёт **топик на каждый аккаунт** и пишет туда
события: 🎯 пойман IP, 🟡 без совпадений, 🔗 привязан к ВМ, ⚠️ ошибка прогона,
🔁 авто-ролл (по расписанию). Так всё сортируется по аккаунтам. Требуется: бот — админ группы с правом
«Управление темами», в группе включены Топики. Если группа не форум или прав нет —
сообщения идут в корень группы (без тредов). thread_id топиков кэшируются в SQL
(`forum_topics`), переживают рестарт.

## Безопасность

Секреты только в env (`${VAR}`), не в репозитории. Неподошедшие IP освобождаются
сразу (иначе капают деньги). Джиттер + экспоненциальный backoff на 429.
Least-privilege токены (Application Credential у VK, сервисный пользователь у Selectel).
